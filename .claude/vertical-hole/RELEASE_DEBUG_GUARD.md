# Bramka bezpieczeństwa panelu testowego — v1.3

## Dlaczego samo ukrycie przycisku nie wystarczy
Niewidoczny CSS, parametr `?debug=true`, hasło w publicznym JS lub `if (PRODUCTION)` z pozostawionym handlerem nie odseparowują panelu. Publiczny artefakt **nie może zawierać kodu panelu, mutatorów danych gracza, endpointów debug ani danych deweloperskich**. Jeżeli repo bez bundlera nie umie tworzyć niezależnych artefaktów, przed GO_TOOLS dodaj oddzielną ścieżkę kopiowania/kompilacji; nie wyprowadzaj GO_TOOLS z samego `NODE_ENV`.

## Wymagana implementacja i dowód
1. Zmapuj realny build i host; dostarcz oddzielne wejście dev/test, importowane **wyłącznie** do dev builda. Przy implementacji dodaj w module panelu jednoznaczny identyfikator tekstowy `VH_DEV_CONSOLE_ONLY`. Musi istnieć w wynikowym artefakcie dev; release nie może go zawierać.
2. Zbuduj **z tych samych źródeł** dwa osobne katalogi: dev oraz release. W katalogach wynikowych nie powinno być sourcemap z kodem panelu, nawet gdy sam interfejs ukryto. Nie testuj katalogu źródeł jako „release”.
3. Uruchom narzędzie z paczki (nie kopiuje plików i nie modyfikuje builda):
   `python .claude/vertical-hole/tools/verify_release_artifact.py --dev-build /path/dev --release-build /path/release`
   Warunek minimalny: identyfikator występuje w dev, nigdzie w release. Jeżeli źródła zawierają inne entrypointy debug, dodaj `--marker NAZWA` dla każdego znanego podpisu. Zapisz komendę, SHA256 całych artefaktów i log.
4. **Niezależnie** przejrzyj listę wszystkich release JS/HTML/maps, globals, sourcemaps, lazy-chunks, serwowane URL-e i wpływ flag/runtime. Negatywny test: otwarcie produkcyjnej strony z `?debug=true`, skrótami i funkcjami console nie otwiera panelu i nie udostępnia mutatorów.
5. Przetestuj izolację: oddzielne profile/key namespaces i SDK sandbox, brak możliwości dopisywania do produkcyjnych sald/rekordów, także po reload, w dwóch kartach, na telefonie. Sprawdź że po dev→prod i odwrotnie dane testowe nie są odczytywane ani migrowane do produkcji.
6. Zarejestruj negatywny test w prawdziwym buildzie każdej docelowej platformy, nie tylko w zwykłym `npm run build`. Release ma osobne adaptery portali.

## Czego skrypt NIE gwarantuje
Brak markera w release to tylko **konieczna, nie wystarczająca** kontrola. Skrypt nie wie, czy deweloper oznaczył wszystkie mutatory, czy manifest serwera prawidłowo wskazuje katalog release, czy ścieżki pod CDN/cache są aktualne. Brak realnego builda/dev preview/fizycznego telefonu = NOT RUN, nie „bezpieczne”.

## Krytyczna regresja w publicznym repo — 2026-10-17 (kontrola v1.4.1)
- W sprawdzonym źródle `vector-hole/main/game.js` panel `class DevPanel` i `window.game.devPanel = new DevPanel(...)` współistnieją z normalną grą, a główny `index.html` ładuje `game.js` bez osobnego builda. **Nie uznawaj istniejącego hasła, ukrytych tapnięć ani sandboxu za dev-only artifact**. Jeśli bieżące repo wciąż tak działa, `GO_TOOLS=FAIL`, `GO_RELEASE=STOP`, a panel NIE wymaga ponownego wymyślania: odseparuj go w osobnym dev entrypoint w osobnym, zatwierdzonym zadaniu.
- `verify_release_artifact.py` sprawdza teraz także **znane podpisy implementacji** (`class DevPanel`, `DEV_ACCESS_KEY`, `DEV_CODE_HASH`, `DEV_SANDBOX_SAVE_KEY`, `devCodeToken(`, `window.game.devPanel`) nawet gdy marker celowo/nieumyślnie zniknął. To tylko negatywny smoke check: obfuskacja/renaming nie dają dowodu bezpieczeństwa; przegląd wszystkich entrypointów i uruchomionego release nadal wymagany.
- Równolegle sprawdzaj workflow przez `python .claude/vertical-hole/tools/check_pages_workflow.py --repo .`. Znane zagrożenie: `.github/workflows/deploy-pages.yml` weryfikowanego źródła publikuje branche `claude/**` i wysyła `path: "."` do Pages. Wymagany projekt osobnego, kuratorowanego katalogu release oraz ograniczone źródła publikacji, weryfikacja wyjściowych assetów i wskazania live URL. **Nie modyfikuj automatycznie workflow w P00** — brak zgody na deploy/zmiany infrastruktury.
- GitHub Pages nie jest „buildem release” tylko dlatego, że skopiowano trzy pliki. W kontekście runtime H5 rozdziel source, QA/debug, dev preview i publishable release. Upewnij się, że URL aktywnej strony serwuje zweryfikowany artefakt, a nie niedawny branch QA; statyczne skanowanie nie jest dowodem serwowanej zawartości.

- **Pułapka testu `qa/dev-panel.mjs` (stan 2026-10-17):** segment „production host (simulated)” (`context.route(PROD + '**', ...)`) przechwytuje żądania adresowane do GitHub Pages i podstawia lokalne bajty z `fs.readFileSync`. Test nie pobiera opublikowanej strony; test `VH_DEV_CODE` na tym symulowanym produkcyjnym adresie oczekuje nawet otwarcia panelu. **Nigdy nie akceptuj raportu tego testu jako dowodu bezpieczeństwa rzeczywistej produkcji.** Wykonaj negatywne testy na prawdziwym live URL bez mocków/routerów, sprawdź serwowany kod i SHA256 każdego krytycznego JS/HTML względem kontrolowanego artefaktu release. Brak możliwości sieciowego potwierdzenia = `LIVE-PRODUCTION=NOT RUN` i `GO_RELEASE=STOP`.

## Krytyczne ograniczenie kontrolera workflow — v1.4.2
Poprzedni `check_pages_workflow.py` błędnie zwracał PASS dla `path: ./`, `path: ${{ github.workspace }}` i push z `feature/**`. Poprawiony skrypt **fail-closed** odrzuca te przypadki, wszystkie nieznane triggery i niejednoznaczne ścieżki; akceptuje tylko jawny `main` przy push (lub ręczny `workflow_dispatch`) i literalny katalog artefaktu w `release/`, `dist/`, `build/`, `public/`, `site/`, `out/` (bez katalogów DEV/QA). Inny legalny model publikacji wymaga rozszerzenia allowlisty z testami, **nie wyłączenia kontroli**. PASS skryptu nie dowodzi, że `main` jest chroniony, środowisko wymaga zatwierdzenia, wybrany folder zawiera tylko produkcję ani że bytes live są zgodne — warunki te nadal sprawdza człowiek oraz PX05.
Przetestuj negatywne fixture'y: `path: .`, `path: ./`, ścieżka dynamiczna, nieznany katalog, `feature/**`, `claude/**`, `pull_request`, brak ograniczenia branches i fałszywe `environment`. Test rzeczywistego RELEASE musi dodatkowo **uruchomić grę**, sprawdzić brak `ReferenceError` po fizycznym wydzieleniu kodu DEV i zgodność entrypointów. Sam brak znacznika/panelu w bundle nie dowodzi grywalności.
